本文档描述完成单个 TODO 任务的流程。

若 /next 的调用参数包含 `loop`，则认为当前处于循环状态；否则为非循环状态。

1. 在 TODO.md 中取第一个未被注释的 `- [ ]` 项，作为实现的目标。
2. 根据该项的内容进行实现细节的确认。

   如果当前并非处于循环状态，可以使用互动式提问确认。

   处于主循环状态时，按以下标准独立确认实现细节：

   - 如果是功能相关的需求，就需要了解实现当前的功能在市面上有什么可用的方案；各个
     方案的易用性、可维护性、可扩展性，最重要的是该实现方案与当前的项目的架构的契
     合程度。
   - 如果是用户体验优化，可以考察当前要优化的部分在市面上是不是有别的应用已经实现
     了类似的功能，检视他们是如何实现这个功能的、如何将这一功能呈现给用户的、为什
     么他们要这样实现、如果使用他们的方案是否能比项目中的现状更好地满足 TARGETS.md
     提出的要求。

   确认实现细节的过程中，获取到的来自项目外的知识里，认为将来可复用的部分，要
   写成 `planning/knowledge/<title>.md`。

3. 得到功能实现细节后，将确认结果写成 `planning/feature/<slug>.md` 文档。
   其中 slug 指的是实现目标的概括性短描述，标题使用小写英文短横线分隔的形式。

   文档必须包含以下小节（中文）：

   ```
   ## 目标      —— 要达成的用户可见结果，引用 TARGETS.md 相关准则
   ## 现状      —— 相关代码/界面现状，列出文件路径
   ## 方案      —— 实现方式与取舍；如做过市面调研，记录备选与选择理由
   ## 验收标准  —— 可验证的条目（含测试/检查方式）
   ## 关联文档  —— 引用的 knowledge/report 文档（若有）
   ```

- 在 TODO.md 该条目下缩进一行注明：`(planning/feature/<slug>.md)`
- 提交：`docs(planning): add feature spec for <slug>`
- **缺少本步骤，禁止开始写测试或实现。**

4. 如果目标是对项目较大范围的重构，需要在开始前将对应功能的实现方式与架构精简地
   写成 `planning/report/<title>.md`（实现细节调查报告），方便后续查询。
5. 先为新功能添加单元测试，完成该步骤后提供工作区的修改。

   在之后的过程中，除非发现测试有 bug，或者新功能的出现使旧测试失去意义，否则不能
   进行单元测试的修改与删除，只能新加。

   并且在该步骤之外发现需要修改单元测试的，都需要把单元测试的修改单独作为一次 git
   提交，在提交信息中注明修改单元测试的原因。

6. 根据已经写好的测试，正式开始由测试驱动的功能开发。完成此步骤后，先不要提交修改。
7. 本步骤进行功能验收。

   如果进行到此步骤时，并非处于循环状态，就发出可以进行本次实现的功能验收的提醒。
   得到验收完成的信号后再提交本次的修改。

   反之，如果该步骤在循环状态下执行，则用以下准则判断功能是否通过验收：

   - 功能符合本次功能文档与 TARGETS.md 提出的要求。
   - 实现能通过所有测试。
   - 若项目中可以添加功能的自动化操作形式的检验，就需要功能能够通过自动化测试。
   - 按照 code review 的要求，进行正确性、边界情况、安全隐患等检查，要求全部通过。

   上述条件有一个条件不满足，都不允许验收通过，进而也不允许进行修改提交、不允许
   进行后续步骤。

8. 验收通过后：
   - 运行 `git add -A`
   - 运行 `git commit`，提交信息用英文 Conventional Commits（如 `feat: ...`），简明描述本次需求
   - 应用 `git log -1 --format=%h` 取得短 hash
9. 处于循环状态时，该步骤什么都不做。反之则回写需求文件。

   把该条 `- [ ]` 改为 `- [x]`，并在同行末尾追加摘要：`→ <关键文件/要点> @<短hash>`
   并提交修改。
