本文档描述本项目中「实现文档」应遵守的标准，供 skill `todo-spec` 读取。
本文件存在时，skill 以本文件为准；本文件不存在时，使用 skill 内置的默认标准。

# 参考知识源（`planning/knowledge/`）（重要）

<!-- 说明 planning/knowledge/ 在确定实现方式时的地位与使用要求。 -->

`planning/knowledge/` 存放项目外、将来可复用的知识（含 `todo-research` 与 `todo-spec`
历次沉淀的调研结论），是**确定实现方式的首要参考**：

- 动笔写实现文档前，先按需求关键词检索并完整阅读相关 knowledge 文档，不要凭印象重做调研。
- 若已有可用方案、依据或适用性判断，`## 方案` 必须建立在它之上并引用具体文档。
- 既有知识与最新调研或代码现状冲突时，说明差异与取舍；必要时补充或更新对应 knowledge 文档。
- 被引用的 knowledge 文档必须列入 `## 关联文档`。
- 已在 knowledge 中的结论改为引用，避免重复复述。

# 文档位置与命名

<!-- 实现文档放在哪里、如何命名。默认：planning/feature/<slug>.md，
     <slug> 为概括性短描述（小写英文短横线分隔）。 -->

- 路径：`planning/feature/<slug>.md`
- `<slug>`：概括性短描述，小写英文短横线分隔。

# 必含小节

<!-- 列出实现文档必须包含的小节及其含义。默认五节如下。 -->

- `## 目标` —— 要达成的用户可见结果，引用 `TARGETS.md` 相关准则。
- `## 现状` —— 相关代码/界面现状，列出文件路径。
- `## 方案` —— 实现方式与取舍；如做过调研，记录备选方案与选择理由。
- `## 验收标准` —— 可验证的条目（含测试/检查方式）。
- `## 关联文档` —— 引用的 `knowledge/`、`report/` 文档（**knowledge 必列**）。

# 提交要求

<!-- 说明提交时机与信息格式。默认：生成新文档后提交
     docs(planning): add feature spec for <slug>，并回写条目 doc 字段。 -->

- 条目 `doc` 为 `-` 时生成文档并提交：`docs(planning): add feature spec for <slug>`。
- 条目 `doc` 已有路径时直接读取，跳过生成与提交。
- **缺少功能文档，禁止开始写测试或实现。**
