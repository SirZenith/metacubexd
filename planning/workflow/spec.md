# 参考知识源（`planning/knowledge/`）（重要）

<!-- 说明 planning/knowledge/ 在确定实现方式时的地位与使用要求。 -->

`planning/knowledge/` 存放项目外、将来可复用的知识（含 `todo-research` 与 `todo-spec`
历次沉淀的调研结论），是**确定实现方式的首要参考**：

- 动笔写实现文档前，先按需求关键词检索并完整阅读相关 knowledge 文档，不要凭印象重做调研。
- 若已有可用方案、依据或适用性判断，`## 方案` 必须建立在它之上并引用具体文档。
- 既有知识与最新调研或代码现状冲突时，说明差异与取舍；必要时补充或更新对应 knowledge 文档。
- 被引用的 knowledge 文档必须列入 `## 关联文档`。
- 已在 knowledge 中的结论改为引用，避免重复复述。

# 必含小节

<!-- 列出实现文档必须包含的小节及其含义。默认五节如下。 -->

- `## 目标` —— 要达成的用户可见结果，引用 `TARGETS.md` 相关准则。
- `## 现状` —— 相关代码/界面现状，列出文件路径。
- `## 方案` —— 实现方式与取舍；如做过调研，记录备选方案与选择理由。
- `## 验收标准` —— 可验证的条目，**每条须以验证手段档位开头标注**（见下节）。
- `## 关联文档` —— 引用的 `knowledge/`、`report/` 文档（**knowledge 必列**）。

# 验收标准与验证手段档位

<!-- 说明验收标准如何书写，避免「人工核对」成为免验证的退路。 -->

`## 验收标准` 是后续写测试与验收的唯一依据，每条都必须在写文档时就说清「用什么手段验证」。

- **每条必须以文字档位开头标注**；档位名固定五个，定义见 `test.md` 的「验证手段档位」：
  **单测** / **假 DOM** / **渲染比对** / **真机** / **人工**。
- **标注不出档位的条目不得写进本节**——先设法变成可验证断言（优先把「看起来只能人工」的
  判断降级为几何 / DOM 断言）；不能则走拆分。
- **单测 / 假 DOM / 渲染比对** 档的条目，必须写明**具体断言位置与比对对象**（测试文件 /
  假件 / 断言什么），不能只写「通过测试」。
- **真机 / 人工** 档的条目：不写进本轮验收标准，改为产出「需拆项清单」，由主会话拆成
  独立 `blocked` 条目（见 `next.md`）。

标注示例：

```markdown
## 验收标准

- [单测] 已完整可见时原地不动 —— 断言于 test/<模块>.test.ts
- [假 DOM] 展开期间内容长高时等到过渡结束 —— 假件：可触发的 transitionend
- [渲染比对] 分组顺序不因改动改变 —— renderToStaticMarkup 逐字节比对（待确认可用）
- [真机] 窄屏下目标不被底栏压住 —— 需真实浏览器，拆条目
- [人工] 视觉上不出现跳变 —— 拆条目
```

# 提交要求
