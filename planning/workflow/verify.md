本文档描述本项目中「验收」应遵守的标准，供 skill `todo-verify` 读取。
本文件存在时，skill 以本文件为准；本文件不存在时，使用 skill 内置的默认标准。

# 通过条件

<!-- 列出验收必须全部满足的条件。默认如下。 -->

- 功能符合实现文档（`planning/feature/<slug>.md`）与 `planning/TARGETS.md` 的要求。
- 实现能通过所有测试；若项目可加自动化形式的检验，须通过自动化测试。可自动化而未自动化的，
  按「人工核对与未实测项」处理。
- code review 关注点全部通过：正确性、边界情况、安全隐患、可维护性。

# 验证手段档位

<!-- 说明本项目可用的验证手段及其优先顺序。无浏览器 ≠ 无验证。验收标准用它做文字标注。 -->

按优先级从高到低，档位名固定为下列五个（验收标准中的标注必须用这些词）：

- **单测** —— 纯函数 / 几何计算，直接断言。
- **假 DOM** —— DOM 行为（滚动、焦点、事件、rAF 时序）：假 DOM + 手动驱动 `requestAnimationFrame`。
- **渲染比对** —— 渲染结果、构建产物比对（<!-- 待确认：本项目是否已验证可行 -->）。
- **真机** —— 真实浏览器。可选增强，需人工在桌面应用中打开本会话；**不作为验收门槛**。
- **人工** —— 以上都覆盖不到的，才走「人工核对」，按下节处理。

**单测 / 假 DOM / 渲染比对** 在纯 TUI 会话下即可完成，是本项目的**默认路径**。

# 人工核对与未实测项

<!-- 说明「人工核对 / 人工验证」类验收项如何处理，避免静默通过。 -->

- 实现文档的验收标准中出现「人工核对 / 人工验证」的条目时，验收**不得**据此判通过。
- 处理方式三选一：
  1. 换成可自动执行的断言（见「验证手段档位」）；
  2. 确实无法自动化的（**真机** / **人工** 档），拆成**独立条目**并置 `status: blocked`，
     标题可用 `- [!]` 作人工标记（语义见 `todo-format.md`），在 `desc` 写明「哪一项留给人工、为什么」；
  3. 明确把它排除出本轮验收范围，并在报告中说明。
- 完成 1) 2) 3) 之后，本条目按**剩余项**判定，**可以判通过**，不因存在需人工的项而卡住循环。
- 验收报告中**必须列出「本条目中未经实测的验收项」清单**；为空是合法结果，但不可省略。

# 判定模式

<!-- 说明循环状态与非循环状态下的验收方式。默认如下。 -->

- 循环状态：由验收执行者按「通过条件」独立判定；任一条件不满足即不通过，禁止提交与后续步骤。
- 非循环状态：产出验收报告后停下等待人工验收；收到通过信号才提交。

# Code review 清单

<!-- 列出本项目验收时重点检查的方面。 -->

- 正确性：逻辑正确、边界与失败路径被覆盖。
- 安全性：输入校验、注入、权限、敏感信息不泄露。
- 健壮性：错误处理得当，不留未处理异常。
- 可维护性：与既有模式/命名一致，无明显重复。
